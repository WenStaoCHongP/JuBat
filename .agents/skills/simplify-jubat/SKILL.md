# JuBat 代码简化

以减少重复职责、嵌套和维护成本为目标；保留计算结果、公开接口、失败语义、状态归属与事件时序。允许代码更清楚但行数略增；不要以删除行数作为验收条件。

## 1. 确认目标与依据

- 定位真实 JuBat 仓库，读取工作树中的 `AGENTS.md` 及目标目录下适用规则；遵守其中当前角色分工。不要推定其他模型就是 zcode。
- 记录仓库 URL、分支、HEAD、工作区改动、目标文件和基准提交。通过连接器读取时固定 SHA；不要把只下载了部分文件的目录当作完整 Git 仓库。
- 用户指定范围时按范围执行；未指定时先看当前 diff 和最近改动，选一个小模块开展。对“全库简化”先列候选，再分批推进；不要一次重写全部物理场。
- 读取 `Simplify/baseline.md`、相关基线的 README、metrics、源码清单及目标调用者。检查入口、脚本哈希和配置是否仍对应当前分支。
- 执行前读 [contracts.md](references/contracts.md)；选验证方案时读 [validation.md](references/validation.md)；选择简化手法或借鉴外部案例时读 [patterns.md](references/patterns.md)。
- 将上述引用视为定位线索。当前源码、适用项目规则和用户已明确的要求优先；不要把技能创建时的快照当作永久配置。

## 2. 把候选分成三类

| 类别 | 处理方式 |
|---|---|
| 保留行为的简化 | 消除完全重复逻辑，缩短控制流，明确局部命名；单批次只处理一个职责 |
| 性能或结构重构 | 先测量并说明拷贝、别名、缓存、求和顺序、线程和 API 风险；满足科学门后才能验收 |
| 科学错误修复 | 单独登记并明确修复范围；不要夹带进“结果不变”的简化提交 |

先制作候选表：文件/函数、重复职责、调用证据、预期收益、等价性论证、验证入口。
用户已授权简化时，对清晰且范围内的可逆变更继续执行；不要逐函数重复请求确认。
删除兼容入口前检查源码、示例、动态 include/参数加载、公开文档和迁出 KB 的测试；仓库搜索无结果不是“外部无人使用”的证明。

已知科学缺陷仅作为重查线索：特别核对 Q4 梯度映射、导热张量交叉项及热生产装配入口。若当前版本仍有缺陷，记录证据；纯简化保持现有行为并明确其科学有效性限制。用户也要求修错时先做独立修复与物理验证，再按项目规则建立获认可的新基线，不要用错误基线证明物理正确。

## 3. 进行一个可回退的批次

1. 在隔离工作树或分支开展；保护用户未提交改动。没有完整 checkout 时可先做连接器审查和可复核补丁，不宣称已经运行本地基线。
2. 保留基准实现与同配置运行证据。解释改动前后输入、输出、副作用和失败边界为何相同。
3. 优先抽出真正重复的纯计算或去掉转发层；使用明确的 `if/elseif` 表达多条件，不压缩成嵌套三元表达式。
4. 保留量纲注释、坐标/节点顺序、状态所有权和回滚解释。只删除过时说明或直接复述语句的注释。
5. 不替换整个 variables Dict 或状态向量布局；不合并具有不同验证口径的生产与验证算子。
6. 不随意删除 `copy`、`deepcopy`、`finally`、有限性/形状/收敛门。先证明生命周期与别名安全；仅在适用 AGENTS 的条件满足后删除被证明冗余的判断。
7. 不把损伤、塑性或温度候选态提前写入已提交状态；失败与拒绝步不得被记成接受步。
8. 保持浮点运算顺序；不要引入 `@fastmath`、并行归约、稀疏散射重排或代数换序来冒充机械简化。
9. 性能手法只用于已确认热点；预分配、views、dispatch 和缓存都须说明收益与责任，避免新增通用框架。

## 4. 验证与推进

- 按 [validation.md](references/validation.md) 运行受影响验证和项目要求的快速门；先比较基准实现与改动实现，再核对有效冻结档案。
- 按项目规定的记录精度、逐位要求或 PNG 哈希验收；不要自行放宽容差、更新期望值或重冻结。
- 正常路径与关键失败/拒绝路径都要覆盖。测试实际改动的生产入口；替代算法通过不代表生产入口通过。
- Julia、依赖、完整源码或 KB 测试缺失时，继续完成独立的静态审查和补丁整理，标注“验证待补”；不得标 PASS、声称仿真通过或声称已符合基线。
- 门禁失败时停止该批次之后的源码变更；定位差异或只回退本批次，保留用户修改和失败证据。
- 已通过后进入下一批；只有新变更、失败或未解决风险才扩大/重复验证。不要为低影响文案与格式改动制造全量测试。

## 5. 交付

报告已简化的职责、为何保持行为、修改文件/提交、实际运行的验证及结果、未完成验证和已知科学限制。
将简化提交与科学修复提交区分清楚。不要只报告删了多少行。
按仓库约定把仿真数据、日志与报告写入 `output/<脚本名>/`；只有实际使用 planning-with-files 时才按 AGENTS 创建任务计划和更新索引。
提交或 PR 描述先说明具体改动与行为，再列必要验证；发布、合并和对外评论按用户明确授权执行。
